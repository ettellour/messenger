# План реализации мессенджера

5 ноября 2026

## Что делаем

Браузерный мессенджер: один сервер на Node.js и одна страница на чистом JS. Четыре функции из задания: вход по уникальному коду, переписка один на один, передача файлов, список чатов.

Задание специально оставляет детали открытыми, поэтому фиксирую допущения заранее:

- Только личные чаты между двумя пользователями. Групповых чатов нет.
- При регистрации пользователь вводит имя, его видит собеседник. Код выдаёт сервер. Пользователь видит его один раз и сам сохраняет. Восстановления кода нет.
- Собеседника находят по id: свой id показан на экране с кнопкой «скопировать», чужой вводится в поле «новый чат». Каталога пользователей нет, чтобы чужие id не светились.
- Файлы до 10 МБ, любого типа. Хранятся на диске сервера, отдаются только участникам чата.
- Данные хранятся в JSON-файлах в папке `data/`. База данных на этом объёме избыточна, а хранилище спрятано за интерфейсом репозитория и заменяется позже.
- Один процесс, без масштабирования. Онлайн-статус и доставка работают в рамках одного сервера.

## Стек

Бэкенд на Node.js 22 LTS без npm-зависимостей: `http`, `crypto`, `fs`, `node:test`. Фронтенд на нативных ES-модулях, без сборщика, браузер грузит файлы напрямую.

WebSocket пишу сам по RFC 6455. Нужны handshake через заголовок `Upgrade`, разбор фреймов с маскированием, ping/pong и закрытие соединения. Если за первые два дня упрусь в баги протокола, беру `ws` как единственную зависимость с пометкой в README, почему.

Границы своей реализации: на handshake проверяется заголовок `Origin`, кадр больше 64 КБ закрывает соединение (всё большое ходит через HTTP), фрагментированные кадры не поддерживаются, клиент шлёт только короткий JSON. Ping раз в 30 секунд, два пропущенных pong значат, что соединение мертво.

Почему отказываюсь от остального:

- Express не нужен: роутов меньше десяти, `http.createServer` плюс один класс-роутер покрывают всё.
- Multipart-парсер не нужен: файл уходит одним `PUT` с телом-потоком и заголовком имени.
- Тест-фреймворк не нужен: `node --test` умеет describe, it и assert из коробки.
- Фронтенд-фреймворк не нужен: два экрана и три компонента, классы на DOM API читаются проще.

## Архитектура

Один класс на файл, зависимости передаются через конструктор. Сервисы не знают про HTTP и WebSocket, репозитории не знают про бизнес-логику.

```
server/
  index.js                    запуск: собирает зависимости и стартует Server
  errors.js                   ServiceError: ожидаемые ошибки сервисов
  http/Server.js              http.createServer, роутинг, раздача public/
  http/Router.js              метод + путь → обработчик
  http/RateLimiter.js         попытки входа и регистрации: 10 в минуту на IP
  http/sessionCookie.js       чтение и сборка cookie сессии
  ws/WebSocketServer.js       handshake на Upgrade, реестр соединений по userId
  ws/WebSocketConnection.js   чтение кадров, события message/close
  ws/frames.js                разбор и сборка фреймов
  auth/AuthService.js         генерация кода, проверка, сессии
  auth/identifiers.js         случайные коды и id в base32
  chat/ChatService.js         найти или создать чат, отправить, список чатов
  files/FileService.js        приём потока, лимит, проверка доступа
  storage/JsonStore.js        чтение и запись одного JSON-файла
  storage/UserRepository.js
  storage/SessionRepository.js
  storage/ChatRepository.js
  storage/FileRepository.js
public/
  index.html
  style.css
  app.js              App: вход, переключение экранов
  api.js              ApiClient: fetch-обёртка с cookie
  socket.js           SocketClient: подключение, reconnect, очередь неотправленных
  chat-list.js        ChatList: список, непрочитанные, свой id и поле «новый чат»
  chat-view.js        ChatView: история, ввод, отправка файла
  format.js           время и размер файла для показа
  ui.js               мелкие помощники: создание элементов, копирование
test/
```

Поток сообщения: `ChatView` шлёт JSON в сокет, `WebSocketServer` отдаёт его в `ChatService`, тот пишет в репозиторий. После записи на диск отправитель получает подтверждение, а второй участник, если он онлайн, получает сообщение через своё соединение. Если он офлайн, сообщение просто лежит в истории до следующего входа.

Сессия живёт в httpOnly cookie. Сокет при подключении читает ту же cookie, отдельной авторизации для WebSocket нет.

`JsonStore` пишет во временный файл и делает `rename`, чтобы падение процесса посреди записи не оставило битый JSON. Записи в один файл выстраиваются в очередь, параллельных записей нет.

## Как пишу код

- ООП там, где есть состояние или замена реализации: соединение, сервисы, репозитории. Чистые функции вроде разбора фрейма в классы не заворачиваю.
- Комментарии на английском и только о том, почему так сделано. Комментарий, пересказывающий код, удаляется.
- Ошибки ловятся на границах: в HTTP-обработчике и обработчике WS-событий. Сервисы бросают исключения и ничего не логируют.
- Абстракции только под реальную замену. Интерфейс репозитория есть, потому что хранилище точно заменится; других прослоек нет.
- Имена говорят о действии: `sendMessage`, `markRead`, `findOrCreateChat`. Никаких `handleData` и `processItem`.
- Логи только в `Server` и `WebSocketServer`: запросы, подключения, ошибки.
- Единый стиль через `.editorconfig`, форматирование без зависимостей в проекте.
- Коммиты по одному законченному изменению, сообщения на английском в повелительном наклонении.

## Данные и API

Пять сущностей. Код пользователя хранится в виде SHA-256. Код случайный, 80 бит энтропии, поэтому медленный хэш вроде scrypt не нужен: он защищает от подбора по словарю, а словаря здесь нет, и перебрать 2^80 вариантов нереально, даже если файл с хэшами утечёт.

```
User     { id, codeHash, name, createdAt }
Session  { tokenHash, userId, expiresAt }
Chat     { id, members: [userId, userId], createdBy, openedByPeer?, lastRead: { [userId]: messageId }, createdAt }
Message  { id, chatId, from, clientId, type: 'text' | 'file', text?, fileId?, sentAt }
File     { id, uploadedBy, name, size, uploadedAt }
```

Id сообщения монотонный: timestamp в миллисекундах плюс счётчик. Иначе курсор `before=` ломается на двух сообщениях с одинаковым временем. Непрочитанные считаются как чужие сообщения в чате после `lastRead[меня]`.

HTTP-часть: только то, что неудобно гонять через сокет: вход, история, файлы.

| Метод и путь | Что делает |
| --- | --- |
| `POST /api/register` | принимает имя, создаёт пользователя, возвращает код один раз |
| `POST /api/login` | принимает код, ставит cookie сессии |
| `POST /api/logout` | снимает сессию |
| `GET /api/me` | текущий пользователь |
| `GET /api/chats` | список чатов с последним сообщением |
| `POST /api/chats` | найти или создать чат по id собеседника |
| `GET /api/chats/:id/messages?before=<msgId>` | история, 50 штук назад от курсора; `after=<msgId>` отдаёт то, что новее |
| `PUT /api/files` | тело: поток файла, имя в заголовке `X-File-Name` |
| `GET /api/files/:id` | отдаёт файл загрузившему и участникам чата, где есть сообщение с этим fileId |

По WebSocket ходят события в JSON, в обе стороны одна форма `{ type, payload }`:

- клиент → сервер: `message.send` (с `clientId`, который генерирует клиент), `message.read` (сдвигает `lastRead` на присланный id), `connection.check` (проверка соединения)
- сервер → клиент: `message.new`, `message.sent` (подтверждение с `clientId` и сообщением), `chat.updated`, `connection.alive` (ответ на проверку), `error`

Сообщения не теряются и не дублируются. Клиент хранит неподтверждённые сообщения в очереди и после обрыва отправляет их снова с тем же `clientId`. Сервер по `clientId` узнаёт повтор, возвращает уже сохранённое сообщение и не рассылает его второй раз. После переподключения клиент догружает открытый чат через `after=` и обновляет список чатов, поэтому пропущенное во время обрыва появляется без перезагрузки.

Об обрыве браузер может не узнавать минутами, а ping сервера страница не видит. Поэтому клиент раз в 25 секунд шлёт `connection.check` и, если за 10 секунд нет никакого ответа, заменяет соединение. Те же 10 секунд отведены на попытку подключиться и на подтверждение сообщения, а HTTP-запросы, кроме загрузки файла, ждут ответа не дольше 15 секунд.

Файл отправляется в два шага: сначала `PUT /api/files`, потом `message.send` с полученным `fileId`. Так сокет не занят большими бинарными кадрами и файл можно переслать повторно без повторной загрузки. Прикрепить к сообщению можно только файл, который загрузил сам отправитель, иначе чужой `fileId` открыл бы доступ к чужому файлу.

Минимум по безопасности, который входит в объём:

- Cookie сессии `HttpOnly; SameSite=Strict`. Это закрывает CSRF без отдельных токенов.
- Текст сообщений вставляется в DOM только через `textContent`. Никакого `innerHTML` на пользовательских данных.
- Файлы отдаются с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`, иначе загруженный HTML откроется и выполнится в браузере.
- `POST /api/login` и `POST /api/register` ограничены 10 попытками в минуту на IP. Код из 16 символов base32 это 2^80 вариантов, с таким лимитом перебор бессмысленен.

## Этапы

Порядок выбран так, чтобы в любой момент была рабочая версия. Если время кончится на третьем этапе, в репозитории всё равно будет вход и переписка с тестами. Каждый этап проверяет второй разработчик: ревью изменений, негативные сценарии и безопасность.

1. Каркас (день 1). Репозиторий, `package.json` без зависимостей, `Server` с раздачей статики, `Router`, `AuthService` с кодами и сессиями, `RateLimiter`, страница входа. Тесты на генерацию и проверку кода и на лимит попыток.
2. WebSocket (день 2). `WebSocketConnection` и `WebSocketServer`: handshake с проверкой `Origin`, фреймы, лимит размера, ping, закрытие. Тесты на парсер фреймов с готовыми байтами из RFC. Здесь же решаю, остаюсь на своей реализации или беру `ws`.
3. Сообщения (день 3). `JsonStore`, репозитории, `ChatService`, события `message.send` и `message.new`, `ChatView` с историей и курсорной подгрузкой. Интеграционный тест: сервер, два клиента, сообщение доходит.
4. Список чатов (день 4). `GET /api/chats`, `ChatList` со своим id и полем «новый чат», событие `chat.updated`, `message.read` и счётчик непрочитанных.
5. Файлы (день 5). `FileService`, `PUT /api/files` с лимитом, отдача по правам и с защитными заголовками, кнопка отправки и имя с размером в чате. Тест на доступ к файлу чужого чата.
6. Доводка (день 6). Reconnect с очередью неотправленных и догрузкой пропущенного, прогон на чистом Arch Linux, README с двумя командами, чистка кода и коммитов.

Ссылку на репозиторий пришлю после первого коммита каркаса.

## Запуск и тесты

Единственное требование к машине: Node.js 22 или новее, это закреплено в `engines` в `package.json`. Никаких `npm install`, shell-скриптов и бинарных модулей. Папка `data/` в `.gitignore`, порт и путь к данным берутся из `PORT` и `DATA_DIR`, тесты поднимают сервер на случайном порту во временной папке и не трогают рабочие данные.

```
npm start    # node server/index.js, порт 3000 или PORT
npm test     # node --test "test/**/*.test.js"
```

Тесты трёх видов: юнит на `AuthService`, парсер фреймов и `ChatService`; интеграционный на полный цикл «сервер, два клиента, сообщение дошло»; один на права доступа к файлу чужого чата; один на лимит попыток входа. Фронтенд проверяю руками в двух окнах браузера. Тестом покрыт только `SocketClient`: его поведение при обрыве зависит от таймеров, и руками его долго и ненадёжно повторять.

## Что не делаю

- Групповые чаты, статусы «печатает», редактирование и удаление сообщений.
- HTTPS: это задача reverse-proxy перед сервером. Пока его нет, cookie идёт без флага `Secure`, в README отмечу.
- Восстановление кода. Потерял: регистрируется новый аккаунт.
- Превью картинок, прогресс загрузки.
- Базу данных и миграции.
